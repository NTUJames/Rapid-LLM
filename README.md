# ECE201C Project 2: Sliding-window Attention

This version adds Gemma 3 local/global attention modeling to the RAPID-LLM course branch.
It includes the required evaluation and two case studies, with a single command to regenerate
the tables, figures, metrics and experiment configs used in the results summary.

**Start here:** [results and analysis](results/project2/RESULTS.md). The included CSVs and PNG/SVG
figures are a compact preview for review. Run details are regenerated by the script below.
The assignment is [PROJECTS.md](PROJECTS.md); implementation hooks are in
[COURSE_README.md](COURSE_README.md).

RAPID-LLM estimates how long a large language model takes to run on given hardware, and how much
GPU memory it needs. It does not run the model. It turns the model shape (layers, hidden size,
heads, experts) into matrix multiplications and other operations, prices each one from the GPU's
compute rate and memory bandwidth, adds communication time when several GPUs work together, and
adds everything up.

No model weights, dataset, CUDA toolkit, actual GPU, AstraSim installation or system Graphviz
executable is needed for these experiments. All hardware numbers come from the repository's
unchanged `configs/hardware-config/course_project/a100_80GB_1gpu.yaml`.

## Setup and one-shot reproduction (WSL/Linux)

After these changes have been pushed to the fork, a fresh checkout is:

```bash
git clone --branch course https://github.com/NTUJames/Rapid-LLM.git
cd Rapid-LLM
```

For a shared source ZIP, extract it and open a terminal in the directory containing this README.
If you already have the local project, use that directory instead of cloning into it.
Create an isolated environment; do not install these pinned versions into Conda `base`:

```bash
conda create -n rapid-llm python=3.12 pip -y
conda activate rapid-llm
python -m pip install -r requirements.txt
python reproduce.py
```

The last command runs correctness checks, all required experiments, both case studies, maximum
batch searches, and generates the figures and tables. It uses CPU for simulation. It can take
several minutes or longer on slower hosts; simulated inference seconds are not script runtime.
Progress is printed after each distinct configuration. No previous result files are read by
the full reproduction command. Repeated identical GEMM problems are memoized within the process,
with the complete problem and hardware parameters as keys, without changing estimated latencies.

Alternatively, with an existing Python 3.12 installation:

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
python -m pip install -r requirements.txt
python reproduce.py
```

Dependencies are pinned in `requirements.txt`: NumPy, Pandas, PyYAML, Python Graphviz and
Matplotlib (headless plotting). Existing `rapid-llm` environments need to rerun the pip command
to pick up Matplotlib; skip `conda create` if the environment already exists. There is no pytest dependency.

Useful alternatives:

```bash
python reproduce.py --verify-only            # quick correctness checks; no full sweep
python reproduce.py --plots-only             # redraw the included snapshot; no simulation
python reproduce.py --output-dir artifacts/my_project2_run
```

The default output is `results/project2/`. The script preserves the old `output/LLM/` and
`artifacts/project2/evaluation/` results. Reusing the same output directory replaces generated
files for those experiment IDs; use a different `--output-dir` to retain an earlier version.

## Metric definitions and interpretation

- **Prefill:** the modeled time to process the prompt once. It is not time to first token;
  the latter also includes the first decode step in this repository's convention.
- **TPOT (ms):** `decode_time / output_tokens * 1000`, per sequence. Do not divide it by batch.
- **Peak memory (GiB):** maximum of prefill and final-decode graph-replayed peaks per GPU,
  including weights, retained KV and modeled activations. Both component peaks are in the CSVs.
- **Fits:** full-precision peak is at most the configured 80 GiB. Display rounding is not used.
- **Max batch:** largest fitting integer batch for that prompt/output/attention configuration;
  the last fitting batch and failing neighbor are checked. Capacity probes use the equivalent
  single-GPU formula `static + max(transient)` to avoid repricing every GEMM.

Dense at the required batch 16 exceeds 80 GiB in this model. Its time is a theoretical
comparison; the hatched bars in Figure 1 are not measured or deployable throughput. Case studies
use batch 4 to keep the dense comparison within capacity; every row still reports its own `fits`.

Local prefill skips tiles outside the causal band and charges intersecting boundary tiles in
full, as the dense implementation does. Local decode/KV use at most the window size; global
layers, projections, FFNs and vocabulary-head activations keep their original sizes. Smaller
windows do not remove those costs. No accuracy/quality evaluation is performed, so the window
sweep measures cost rather than recommending a replacement model configuration.

The inherited memory model includes vocabulary-head output activations for the whole prefill
prompt, which can dominate peak memory. KV-cache savings therefore do not imply the same
percentage reduction in overall peak. This is the repository's model, not a claim that a serving
engine must materialize full-prompt logits or that actual Gemma serving has these exact peaks.

Scope is single-GPU analytical inference with dense MHA/GQA and FlashAttention prefill.
Training, MoE/MLA local attention, multi-GPU local attention and AstraSim local attention are
rejected. Energy counters are inherited from the original simulator and are not part of the
validated study metrics. These results do not measure end-to-end serving overheads or model quality.

## Running one config

```bash
python run_perf.py --hardware_config configs/hardware-config/course_project/a100_80GB_1gpu.yaml \
                   --model_config configs/model-config/course_project/Llama3.1-8B_inf.yaml
```

Results go to `output/LLM/`: `LLM_inference_results.txt` repeats the summary, and
`memory-summary/memory_capacity_comparison.txt` gives the prefill, decode and maximum peak memory
per GPU. The lines that matter on screen:

```
[decode] sample step 0: seq_len=1025, time=0.0121s
[decode] sample step 1023: seq_len=2048, time=0.0122s
[prefill] time: 0.0661s, [decode] time: 12.4618s, [total] time: 12.5279s
[kv-cache] prefill_store=0.1 GiB, decode_store=0.1 GiB, decode_fetch=192.0 GiB
LLM time to first token: 0.08s
Aggregate decode throughput tok/s (batch=1, replica_count=1): start=82.40, mid(token 512)=82.17, end=81.94
```

- `sample step`: one decode step (one new token for every sequence) at that context length.
- `prefill` processes the prompt once; `decode` generates all output tokens; time to first token
  is prefill plus the first decode step.
- `kv-cache`: key/value bytes written in prefill and decode and read in decode. `tok/s`: tokens
  per second over the whole batch at the start, middle and end of decoding.

## Changing the inputs

In the model YAML, under `model_param`: `global_batch_size` is the number of sequences served
together (B), `decode_len` the decode (output) tokens per sequence, and `seq_len` the prefill plus
decode tokens; to change only the output length, change both by the same amount. Under
`inference_param`, `sample_every: -1` (the default) prices only the first and last decode step;
`sample_every: N` also prices every Nth step.

Your own inputs (link bandwidth and latency, window size, block size, number of guesses, and so
on) go in a `project_param:` block in the model YAML; see H1 in [COURSE_README.md](COURSE_README.md).

## How a decode step is priced

1. `TimeCalculationLLMInference.calc_total_inference_time` (inference_timing.py) runs prefill
   and peak memory in `calc_time`, then decode in `calc_decode_time`, which hands over to
   `DecodeGraph.build_decode_graph` (simulate_inference_graph.py).
2. `build_decode_graph` picks the sampled steps (`_generate_sample_points`; by default only the
   first and last step), computes the GEMM shapes for the current context length
   (`llm_util.process_decode_gemm_shapes`, which calls `autoregressive_decoder_gemm`) and calls
   `_execute_decode_step`.
3. `_execute_decode_step` makes a fresh timing object and calls `prepare_decode_graphs`
   (inference_timing.py).
4. `prepare_decode_graphs` calls `_build_decode_transformer_results` for a dense layer and, for
   sliding-window models, a local layer at a bounded KV context (or an MoE layer for MoE models).
   Each call returns a table of operations (`qkv_proj`, `attention`,
   `ffn1`, ...) and a `node_breakdown` holding the per-layer time `transformer_time_f` and the
   output-head time `linear_softmax_f`.
5. `_prepare_execution_graphs` (train_timing.py) turns these into a graph of layers
   (simulate_train_graph.py), and `LLMExecutionDispatcher.run` (llm_execution.py) returns the
   step time.
6. `_integrate_decode_samples` joins the sampled steps with straight lines (trapezoid rule) to
   get the total decode time. Sliding-window models add samples around window saturation.

Peak memory: `calc_time` calls `MemoryEstimator.build_memory_data` (memory_estimation.py) for
weights, KV cache and activations, then `simulate_peak`, which replays the layer graph
(simulate_train_graph.py). Going over the GPU's memory prints a warning; it does not stop the run.
